## What this repo is

A Reactome curator-assist tool that uses LLMs to draft annotations from literature. It has **two separate entry points** that share an install and `.env`:

1. **Gene-first CLI pipeline** (legacy, flat scripts + `reactome_llm/`): `python run_curator.py GENE` → placement → PubMed retrieval → full-text reaction extraction → QA. Output in `results/`.
2. **Paper-level REST service** (`curator_llm/`, FastAPI): annotates ONE paper (PMID or uploaded PDF), verifies quotes, resolves identifiers, emits staged instances, lists issues, and supports chat-based edits as *proposals*. Used by curator-tool-frontend (Angular, "Paper2Path" page). Most active development is here.

Python 3.10, conda env `reactome_ai`. Needs Neo4j (Reactome graph, `:7687`), MongoDB (`:27017`), `ANTHROPIC_API_KEY` (OpenAI key only for the optional cross-model review). Config is in `.env` (copy `.env.example`; loaded with `override=True`, so active values beat the shell).

## Commands

```bash
pip install -r requirements.txt            # authoritative dependency list
pytest                                      # tests/ (pytest.ini); all external services are faked
pytest tests/test_patching.py -k name       # single test
scripts/run_api.sh [--reload|--daemon|--stop]   # run REST API (uvicorn curator_llm.main:app, :8000, docs at /docs)
python scripts/export_openapi.py            # regenerate docs/openapi.json
python scripts/make_snapshot.py             # build a snapshot for replay mode
python run_curator.py SHANK3 --no-full-text --no-llm-review --no-llm-qa   # cheap CLI smoke test
```

`tests/test_ws_contract.py` needs a real curator-tool-ws plus `WS_USERNAME`/`WS_PASSWORD`; it is not part of normal offline runs.

## REST service architecture (`curator_llm/`) — ports & adapters

- `main.py` — production wiring (`build_app()`; `app` is created at import unless `CURATOR_LLM_AUTOSTART=0`). Reads env: `WS_BASE_URL`, `SESSION_STORE=file|mongo|memory` (default file, under `SESSION_DIR`, default data/sessions), `SNAPSHOT_MODE=record|replay|off`, `SNAPSHOT_DIR`, `CHAT_MODEL`, `CORS_ORIGINS`, `UPLOAD_DIR`, `LLM_REVIEW`.
- `api/app.py` — `create_app(...)` takes all dependencies by injection; routes under `/api/llm`: sessions (create / upload / get / issues / usage / export / network / existing / qa / paper search), evidence per instance, proposals (create / accept / reject), chat (SSE stream), jobs. Every request is authenticated and requires the `curator` role (401 / 403); sessions are private to their owner (others get 404).
- `ports/` — interfaces (`AuthProvider`, `InstanceLookup`, `JobRunner`, `Pipeline`, `Extractor`, `ChatModel`, `SessionStore`, external UniProt/OLS clients, events). 
- `adapters/` — production implementations: ws token verification (`ws_auth`, calls curator-tool-ws `GET /api/auth/verify`), Neo4j lookup, UniProt, OLS, Anthropic chat, in-process job runner, session stores (file, the default: `sessions_file`, one JSON per session in a folder per user; Mongo; memory).
- `models/` — pydantic: `reactome.py` (typed `ReactomeDraft`), `evidence.py`, `session.py`, `usage.py`.
- `services/` — the logic:
  - Pipeline: `pipeline_default` (paper → extract/merge/review → verified evidence → typed draft → resolved ids), `extraction` (wraps the legacy scripts), `paper_loader`/`paper_text` (PDF via PyMuPDF or PMC JATS XML, offset-tracked), `quote_verifier` (deterministic, normalised matching), `evidence_attach`/`evidence_store`, `draft_builder` (one structured LLM call, then code), `resolvers` (names → dbIds; **the LLM never supplies a dbId**), `emitter` (draft → frontend `UserInstances` JSON; new instances get negative dbIds), `existing_events` (does Reactome already have this reaction), `qa`, `issues`, `network`, `schema_index`.
  - Editing: `patching` (RFC 6902 JSON Patch on the draft, reaction keys allowed in paths), `chat_agent` (tool-use loop that can read and *propose* only), `session_service` (owns the session lifecycle; **all store writes go through it** and it re-emits instances/issues on change).
  - `snapshots` — saves each successful run (10–15 min of LLM calls) keyed by PMID/PDF hash + focus gene; `replay` mode reuses them for UI work and demos.

Key invariants:
- Edits only take effect after a curator accepts a proposal. An edit changing what a reaction *is* (inputs, outputs, catalyst, regulators) needs a quote found in the paper, or must be marked a curator assertion.
- This service never writes to gk_central; commits go frontend → curator-tool-ws.
- Keep `WORKERS=1`: jobs run in-process and (with the memory store) state lives in the process.
- Speed: extraction runs chunks concurrently (`EXTRACT_WORKERS`, default 16; `1` = old serial mode where each chunk sees notes on the previous two, otherwise it sees the raw previous chunks), the extraction and duplicate-judge prompts are prompt-cached, and `run_merge.py` skips pairs that share no input/output entity (`services/dedup_prefilter.py`, `--no-prefilter` to disable). Which model each step uses lives in `curator_llm/model_settings.py` (roles + `LLM_MODEL_<ROLE>` / `LLM_THINKING_<ROLE>` overrides); add new LLM calls there, never hardcode a model id. Extended thinking is OFF for extraction and merge: it was most of the output tokens and latency, with no measured quality gain. Don't use Haiku as the duplicate judge (missed 10 of 24 merges). PINK1.pdf: extraction ~32s, merge ~44s (was ~5+ min and ~77s).
- A paper with no Results section (short communication, review, author manuscript) is extracted from the whole paper (`whole_paper` in `reactome_llm/FullTextPDFSections.py`: Abstract to References), flagged `via whole-paper` (no LLM boundary guess, which was not repeatable on such papers); the old behaviour was to abort.
- Direct evidence: each paper is research or a review (`PaperRef.review`, None = decide). `services/paper_kind.KindPipeline` wraps the snapshot layer and decides first: an explicit setting wins (REST `review`, upload `review_files` per PDF, CLI `--review`); a PMID uses PubMed's publication type (`adapters/pubmed.py`, port `PublicationTypes`); a PDF is research; PubMed unreachable means research plus a `paper_kind_unknown` issue. The decision comes back in `PipelineResult.reviews` and is shown in `Session.papers[].review`. For research, `run_extraction.py` drops reactions whose every quote has `claim_origin: cited` (`services/direct_evidence.py`, in code, not the prompt) into `<stem>_cited_only.json`; `SubprocessExtractor` turns that list into a `cited_only_left_out` info issue. A review keeps them. `review` is part of the snapshot key (`+review`). Not inferred from the missing Results section (short communications and author manuscripts lack one too), nor from PMC's JATS article-type (it calls review 23256519 a research article).
- A PDF's PubMed ID: `services/paper_identity.py` finds it (DOI on pages 1-2, accepted only when PubMed's title is printed there; else the page-1 title, stopwords out of the `[Title]` query, partial titles compared with the start of PubMed's) via port `ArticleSearch` (`PubMedClient.search/titles`, rate-limited). Only offered: `POST /papers/identify`, `POST /sessions/{id}/papers/identify`. Given as `PaperRef.pdf_pmid` / `PipelineInput.pdf_pmid` (upload `pdf_pmids`, checked against PubMed): extraction still reads the PDF (source tag stays the file name); `paper_kind` asks PubMed for it; `SessionService.cite_paper` puts it on the paper's reactions, quotes and pathways after the run, and `set_paper_pmid` (`PUT /sessions/{id}/papers/pmid`) sets, changes or removes it later.
- Extraction prompt excludes hypotheses/model predictions, cell-level outcomes, intra-complex structural contacts and tool-only events, and gives a modification site only to the enzyme its sentence ties it to. The merge judge treats fewer named sites (a subset, or none) as less detail; disjoint site sets stay different. Changing the judge rules changes `_RULES_FP`, so cached verdicts are not reused.
- Draft entity kinds are protein | gene | rna | small_molecule | complex | set. A gene or transcript is an `EwasSpec` with `molecule='dna'|'rna'` (emitted with a ReferenceDNASequence / ReferenceRNASequence, no UniProt lookup); promoters/E-boxes are not entities, they are regions of the gene entity. `small_molecule` is for chemical compounds only.
- Non-human molecules (host-pathogen papers): the draft step gives a protein/gene/rna of another organism a `species` and its UniProt gene name (KSHV LANA is LANA1). `Resolver._organism` finds the Species (`neo4j_lookup.find_species`, by name or synonym, with taxId), then the accession in that species (`find_accession`: gene name, short name, then a unique gene-name prefix for non-human only) or UniProt by `taxonomy_id` (strains included; human keeps `organism_id`), and renames the entity to the UniProt gene name with a note. An organism Reactome lacks is flagged, never searched. Emitter follows Reactome: the viral EWAS/reference has the virus as species; a complex/set with a human part, every reaction and pathway is Homo sapiens with the virus as `relatedSpecies`; an all-viral complex is the virus.
- The job's `progress` text is live: `SubprocessExtractor` streams the scripts' output through `StepProgress` (chunk counts, merge stages); `Extractor.extract` takes an optional `report` callback, and `DefaultPipeline` passes it only to extractors that accept it. Identifier lookups in `Resolver.resolve` run in parallel (`RESOLVE_WORKERS`, default 8) with notes kept in task order. Restart the service after changing in-process code.
- QA (`services/qa.py`): findings are sorted most serious first and capped; `priority` (fix_first/fix/review/ok) is derived in code from the action-finding count, and `POST /sessions/{id}/qa` checks every reaction concurrently and returns them ranked. A binary verdict was needs_work for every reaction, so rank, don't threshold. The model call runs outside the session lock. With `AUTO_QA` (default 1; `create_app(auto_qa=)`, `SessionService(qa_model, auto_qa)`) every reaction of a new draft is QA'd by the model before the session is ready (`SessionService.qa_into`), except for a replayed run; the CLI does the same unless `--no-qa`. The QA prompt first asks whether it is a molecular reaction at all (phenotype, structural contact, hypothesis, step rationale, tool event, negative result -> an action to remove it).
- Production (aws_curator_new, /usr/local/reactomes/Reactome/production/webbench/curator-tool-llm): `scripts/deploy-production.sh`. The app runs from the folder's `.venv` via `../manage-apps.sh start|stop llm` on 127.0.0.1:5000 behind Apache `/llm/`; several users deploy there, so the code must stay group-writable and `.env` readable by whoever starts it.
- Deployment: `scripts/deploy.sh user@server` (see README, "Deploying to a Linux server"). The REST service's file set is explicit in that script (service modules, 6 reactome_llm files, 3 run_*.py, the domain schema); add any new file the service loads by path to `SERVICE_FILES`, and any new third-party import to `requirements-service.txt`. Its import check runs from the unpacked archive and will catch a miss.
- Merging (`run_merge.py` + `services/merge_support.py`): every quote carries its own paper (`evidence_details[q]['source']`, `Evidence.source`); identical reactions fold within a paper only; clustering is per connected component; judge verdicts are cached in `data/merge_cache/judge.jsonl` (`--no-cache`). With more than one paper in the input (several extraction files + `--out`), `merge_across_papers` merges across papers incrementally (best candidates first, at most 10 per reaction, stop at the first same, identical signatures free, a reconcile pass; `--no-cross-paper`, `--cross-max-candidates`, `--cross-all-pairs` as the exact reference). The REST service is still one paper per session. `run_merge.py` runs its driver at import: keep logic in `merge_support.py` where it can be tested, and avoid reusing helper names (`_key`) as loop variables there (`tests/test_run_merge_script.py` runs the script with a stub model).
- Several papers per session: `PipelineInput.papers` (`PaperRef`s), `SubprocessExtractor.extract_many` (each paper extracted, then ONE `run_merge.py` over all files), `Session.papers` / `paper_texts` (every paper's text by source tag), `Evidence.source`, `SessionService.papers_of` / `search_papers` / `_verify_evidence` (quotes may come from any paper). REST: `POST /sessions {pmids}`, `POST /sessions/upload` with `files` + `pmids`; limits `MAX_PAPERS`, `PAPER_WORKERS`. Command line: `scripts/annotate_papers.sh` runs the pipeline IN-PROCESS (`curator_llm/cli.py`, wiring shared with the service in `curator_llm/wiring.py`): no service, login or paper cap (MAX_PAPERS is the service's); merged by default, `--separate` for one draft per paper; writes staged instances, issues, session and evidence files.
- Checks and suggestions: QA rules in `qa.AUTO_RULE_CODES` run on every `SessionService.refresh`: structural ones, quote-wording ones (`qa_only_cited` incl. a this_paper quote carrying "(ref. N)", skipped for review papers via `SessionService.reviews_of`; `qa_negative_only` / `qa_hedged_only` judged on the quotes that state a result; `qa_methods_only`: Methods section or a figure-panel legend opening, since PDF quotes often have no section), and `qa_possible_duplicate` (`duplicate_findings`: same catalyst, inputs/outputs overlapping by the smaller side; with no catalyst both must have outputs and agree on regulators). All appear as issues with source `checks` (replaced each refresh; QA runs skip those codes so they are not doubled). `services/suggestions.py` makes fixes with one clear answer (consumed enzyme, missing PMIDs, and `remove_reaction` for `qa_only_cited` / `qa_negative_only`: out of the pathway and preceding lists, then the reaction) as pending proposals with actor `suggestions` (`SessionService.refresh_suggestions`, after the pipeline and after each accept; `POST /sessions/{id}/suggestions`; `.suggestions.json` from the CLI). **Never auto-apply a fix**: the curator decides. Suggestions skip the quote requirement (`_build_proposal(skip_evidence_check=True)`). Reactions about genes/transcripts are not compared with existing events (no UniProt accession), and a gene/transcript reuses Reactome's HUMAN ReferenceDNA/RNASequence (`Resolver.reference_sequence`; the species of a reference sequence is a graph relationship, read in `neo4j_lookup._RETURN`).
- Issue list for curators (`issues.organize`, run after every refresh, suggestion refresh, QA and issue status change): each Issue gets `category` (keep | existing | content | identifiers | evidence | paper | other), `blocked_by` (the open keep issue of its reaction, or of every reaction using its entity; entity notes are linked by their "NAME: ..." prefix) and `proposal_id` (the pending suggestion that fixes it). Keep issues (`issues.KEEP_CODES`: QA's `qa_not_a_reaction` from the reply's `is_reaction` field, and the cited/negative/hedged/methods-only checks) each come with a `remove_reaction` suggestion; the frontend shows them first as Remove/Keep decisions, hides blocked issues and notes by default, and groups the rest by reaction ordered by `Session.qa[key].priority`. Removing a reaction drops its issues and QA. A paper without PMID is one `paper_no_pmid` issue, not one per reaction. On WEE1/CDH1: 242 open issues became 18 decisions plus 89 issues on 12 reactions and 25 on entities/the paper.
- Removing a reaction: `DELETE /sessions/{id}/reactions/{key}` (`SessionService.remove_reaction`) builds the same patch as the `remove_reaction` suggestion (`suggestions.remove_reaction_ops`) and applies it through `_apply`, the body of `accept`, as an accepted proposal with the curator as actor and no quote check. `_apply` also marks every other pending non-suggestion proposal that no longer applies as `stale`. Frontend: the reaction panel's Remove button; the workspace re-reads everything, moves the selection and drops the key from the checked-to-load set in `followRemovals()` (for removals from any path), bumps `draftStamp` only after that, and the chat panel re-reads proposal statuses on that stamp.
- Command-line results in the front-end: `cli.annotate` also writes `<name>.annotation.json` (the whole `Session`, owner `local` unless `--owner`); with `--owner USER` it is saved into the file session store too (`--session-dir`, default `annotation_files.default_session_dir()`). `curator_llm/annotation_files.py` (`scripts/import_annotation.sh`, shipped by deploy.sh) adds such files to a user's folder later; the session id is kept, so adding the same file twice is refused unless `--replace`.
- Resuming large CLI runs: `run_extraction.py` retries a transient model error (`EXTRACT_RETRY_WAITS`), records a chunk that still fails (`ChunkFailed`, `FAILED_CHUNKS`) and writes `<stem>_extraction.status.json` (`complete` / `incomplete` / `no_text`, with a `fingerprint` of paper content, model settings, prompt head, serial mode and review); the old status is deleted when an extraction starts. `--resume` reuses a complete extraction with the same fingerprint. `SubprocessExtractor(resume=)` passes it (the CLI sets it unless `--force`; the service never does) and fills `ExtractionResult.paper_status`; an incomplete paper stays out of the merge; `ExtractionResult.complete` / `PipelineResult.complete` also need `merge_ok`. `SnapshotPipeline` does not save an incomplete result. `PipelineFailed` carries `paper_status`. The CLI writes `<name>.progress.json` and skips a run only when it is `complete` (or, from before progress files, when its staged file exists).
- Spreadsheet runs: `curator_llm/spreadsheet.py` (`scripts/annotate_spreadsheet.sh`) reads an .xlsx with the standard library (no openpyxl in the env), plans a PDF or a PMID per row, downloads PMC JATS into `PMC_CACHE_DIR` (now read by `PubMedFetcher.CACHE_DIR`, inherited by the extraction subprocesses; default data/pmc), and runs `cli.annotate` per paper (or per `--group-by` value), writing `summary.tsv`. A run whose papers were all read completely but gave no reactions ends `no_reactions` (`cli.EMPTY`): finished, not retried.
- Pathway hierarchies: `PathwaySpec.subpathways` (nested; `walk()` yields JSON paths); the emitter emits sub-pathways as events of their parent, `integrity_errors` and `remove_reaction_ops` cover every level. `services/combine.py` builds one annotation from finished per-paper sessions (top -> group -> paper pathways): participants shared by identity (accession or ChEBI + normalized name + modifications + compartment; complexes by name and parts), reaction keys prefixed per paper, and within a group reactions the duplicate judge calls the same folded into one listed under each paper (`merge_across_papers`; the judge runs in-process via `merge_support.make_judge`; its brief and rules moved from run_merge.py to merge_support.py unchanged, so the cache keys stay). Used by `annotate_spreadsheet.sh --hierarchy`.
- All measurements behind the speed/quality defaults (timings, model comparisons, accuracy vs curated Reactome, bugs found, what is untested) are in `docs/performance-tuning-results.md`.
- `scripts/ground_truth_eval.py` scores extraction/merge settings against the curated reactions Reactome holds for a paper (needs Neo4j; `run PMID...` then `score PMID...`; resumable). On 8 papers (6 research, 2 reviews) the new defaults matched the original pipeline's recall (29/41 vs 28/41 on research papers, 12/20 vs 12/20 on reviews) with higher entity recall (80% vs 66% on research papers). The pre-filter and merge thinking made no difference to recall, and the pre-filter skipped 80% of pairs on a 150-reaction review. Not every PMID with a PMC id has full text: check `fetch_jats` returns a body.
- Extraction/merge/review still run as **subprocesses** (`run_extraction.py` → `run_merge.py` → `run_review.py`) on purpose, because merge/review keep state in module globals. Don't delete those scripts or inline them casually.
- Tests use fakes in `tests/fakes/ports.py`; the PINK1 paper (Kane et al. 2014, PMID 24751536) is the golden fixture.

## Gene-first pipeline (legacy)

`run_curator.py` runs three synchronous agents: Curator (`reactome_llm/ReactomeCurator.py`: placement, literature retrieval, full-text resolver, full-text analysis), Reviewer (`ReactomeReviewer.py`, decides sufficient/retry/give_up; retry cap lives in `run_curator.py`), and QA (`ReactomeQA.py`, using `reaction_to_instances.py`, schema checks vs `resources/reactome_domain_model.json`, Neo4j merge check, LLM review). Full-text extraction (`fulltext_extractor.py`) shells out to the `run_*.py` scripts. Mongo holds two DBs: PubMed abstract cache and functional-interaction partners (`idg_pairwise`). A FAIL/NEEDS_REVISION QA verdict is normal output, not a bug.

Other: `dense_retrieval/` is an experimental embedding investigation; `abstract_extractor.py`, `TextEmbedder.py` are standalone helpers; `docs/openapi.json` is generated.

## Conventions and gotchas

- Dependency injection through ports; add new external access as a port + adapter + fake, not by importing clients in services.
- Gitignored local data: `data/` caches (`snapshots`, `uploads`, `fulltext_*`), `results/`, `logs/`, `.env`, `resources/interactions/`.
- Related repos (same workspace): curator-tool-frontend (Angular UI), curator-tool-ws (Java; auth verify, gk_central reads/commit).
- Untracked scratch files in the root (`chainlit.md`, "Review curator-tool-llm …md") are not part of the code.
